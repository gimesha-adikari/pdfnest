## Synthetic fixture set

`tests/security/milestone-1/generate-fixtures.ts` creates seven small files from deterministic, fixed-metadata `pdf-lib` sources, then uses installed `qpdf` to produce independent encrypted variants. Encryption uses randomized ciphertext, so byte hashes can differ between runs; the script prints SHA-256 per generated artifact for each run rather than asserting a fixed encrypted-file digest. No binary PDF is committed.

| Fixture | Format/pages | Marker | Protection and test password | Independent verification |
|---|---|---|---|---|
| `plain-two-pages.pdf` | Valid PDF, 2 pages | `PLATEN_M1_SYNTHETIC_ALPHA`, `PLATEN_M1_SYNTHETIC_BETA` | None | `qpdf --check`; `pdfinfo` page count; `pdftotext` marker extraction |
| `protected-alpha.pdf` | Valid PDF, 2 pages | Same two markers | AES-256; user `platen-m1-user-alpha`, owner `platen-m1-owner-alpha` | Correct password accepted by qpdf/pdfinfo/pdftotext; `pdfinfo` reports `Encrypted: yes`; wrong password rejected by qpdf |
| `protected-beta.pdf` | Valid PDF, 2 pages | Same two markers | AES-256; user `platen-m1-user-beta`, owner `platen-m1-owner-beta` | Correct password accepted by qpdf/pdfinfo/pdftotext; `pdfinfo` reports `Encrypted: yes` |
| `protected-lock-output-aes128.pdf` | Valid PDF, 2 pages | Same two markers | AES-128 (AESv2); user and owner `platen-m1-user-alpha` | qpdf `--show-encryption` reports AESv2; correct password and content validated independently |

The user passwords are synthetic test data, not credentials. Fixture creation requires existing `pdf-lib`, `qpdf`, `pdfinfo`, and `pdftotext`; no PDF package was installed. qpdf 12.3.2 is available in the inspected environment. qpdf does not allow `--deterministic-id` with encrypted output; the generator therefore fixes source metadata and content but lets qpdf generate encryption randomness. The per-run hashes preserve evidence of the exact artifacts used.

## M1-S1-02R route-level venue policy

`getProtectedPdfRoutePolicy` derives each landing-page policy from the actual tool registry's PDF accept metadata, execution policy, client capability, and offline-workspace capability. Explicit registry overrides identify Unlock and Studio V2. The resulting classes are:

| Route class | Protected-input behavior | Examples |
|---|---|---|
| Device/Auto/Cloud through `ExecutionManager` | Protected input may be prepared locally; selected mode is carried into its workspace. | Merge, Rotate, and other registered client-capable offline workspaces |
| Cloud-only direct/API/queued | No Device choice is shown. Protected input can be locally unlocked, then the user must authorize this specific tool's Cloud submission. The submit handler rechecks authorization immediately before sending. | PDF-to-Word, Grayscale, PDF-to-Markdown, PDF Editor, Redact, OCR Text V2, OCR-aware Markup V2, Structured Document V2 |
| Cloud-capable direct branches | Protected input has no Device choice because these workspaces do not carry the selected venue into every direct submission branch. The route requires scoped Cloud authorization before the workspace opens, and direct worker helpers recheck it. | Legacy Highlight, Underline, and Strikeout OCR/worker branches |
| Explicit Unlock | The intentional unlock operation accepts the source without the ordinary preparation prompt. | Unlock PDF |
| Studio V2 session consent | Its existing inspection bypass is retained; session upload waits for affirmative Cloud-upload consent. | PDF Studio V2 |
| Unqualified or non-PDF route | Protected, derived, or unverified inputs fail closed before the workspace can submit. Image-only searchable-PDF routes are not classified as protected-PDF processors. | Unregistered legacy `/studio`, `/searchable-pdf-v2`, `/image-to-searchable-pdf`, and future unqualified routes |

Direct Cloud workspaces enforce a route-scoped authorization both at the shared workspace gate and immediately before their processing endpoint. Plain PDFs inspected as unprotected retain their existing Cloud workflow without the additional protected-input consent. Cloud-unlock consent does not authorize a later Cloud-processing request. PDF-to-Text's explicit Cloud OCR submission has a separate confirmation for protected or unverified sources; Auto fallback remains governed by the existing Auto contract. Structured Document V2 may load service capabilities before consent, but the protected document is not included until its user-triggered job submission passes the guard.

The Processing Mode selector uses one eligibility function for its Device button and Cloud-offline alternate. If the current file or any file in its batch was already sent to Cloud, Device is unavailable and the transmission warning remains visible. `ExecutionManager` also rejects a stale explicit Device request for a Cloud-transmitted input locally, before invoking either executor. Auto and Cloud behavior are unchanged. A protected file transferred with Cloud-transmission provenance opens in Cloud mode; the uploader preserves that marker through reinspection, preparation, and explicit Unlock input. Device is not reoffered for that source.

Mixed input preparation keeps the original selection list and replaces each protected source at its original index after preparation. Password entry remains scoped to the first protected source in queue order. Tests cover Plain A + Protected B + Plain C and Protected A + Plain B + Protected C, including distinct alpha/beta passwords and cancellation.

Cross-tool transfer carries only transient protection-lineage and Cloud-transmission booleans with the in-memory Blob. The destination creates a new File and re-inspects its bytes; source protection is not inferred as output encryption. Derived or previously Cloud-transmitted inputs require target-route Cloud authorization when sent to a direct Cloud route. This does not define output encryption or resolve F-02.

The 26-case Playwright suite in `tests/security/milestone-1/protected-input-privacy.spec.ts` passed against a local Next.js app, synthetic fixtures, request interception, and local API mocks. It includes PDF-to-Word and queued Structured Document submission ordering/payload checks, separate Cloud OCR authorization after Cloud unlock, protected-input annotation route consent, offline-selector lockout, normal Device/Auto/Cloud selection for plain PDFs, mixed Merge order/passwords, cancellation/stale-response cases, Cloud-prepared cross-tool transfer to PDF Editor, plain PDF behavior, Unlock, legacy Studio fail-closed input, and Studio V2 upload consent. It proves the tested browser-to-mock request boundary only. It does not establish real-backend behavior, production browser behavior, every direct legacy Studio endpoint, or protected output publication. F-01 remains open and F-02 remains unresolved.

## M1-S1-02R2 consent and result-provenance correction

Cloud authorization and transmission history are separate transient facts. `authorizeCloudProcessing()` records tool-scoped consent only; it does not claim a request began. Transmission risk is recorded immediately before the HTTP submission in the shared upload helper, the queued-task submission helper, and the direct editor/OCR/annotation/Studio V2 submission helpers. `ExecutionManager` does not mark a request merely because it selected Cloud; permitted Auto fallback still reaches Cloud through the same request boundary. A started request retains its risk marker after a failed response or cancellation. User-facing wording says delivery may have occurred, not that delivery was confirmed.

Plain inputs that were inspected as unprotected remain eligible for same-route retries after a Cloud request starts. Protected, unchecked, or transferred inputs still require fresh tool-scoped authorization when appropriate. Consent does not move to another File or destination tool. Cross-tool transfer re-inspects destination bytes and retains source lineage and submission history separately.

Result provenance is captured at result acceptance. Merge snapshots the exact submitted queue and order after additions, removals, and reordering; later workspace changes cannot alter that immutable snapshot. The download/transfer path carries the result snapshot in transient in-memory context rather than deriving it from the original landing File. Provenance contains no password, and protected-source lineage does not claim the output itself is encrypted. Destination preparation inspects output bytes independently and does not inherit source-route consent.

The Playwright privacy suite includes plain PDF Editor extraction/retry/compile, plain conversion retry, protected Auto OCR fallback success/retry failure/task cancellation, all three protected annotation-analysis routes, Merge queue result transfer and target authorization, and existing replacement/cancellation/Device/Unlock/Studio V2 cases. ## M1-S1-03 Legacy Studio protected-input qualification

The source review found a reachable bypass in `.pns` project import and IndexedDB recovery: each path reconstructed or restored embedded PDF Files directly, while activating a document automatically starts a Cloud preview session. Raw PDF uploaders were already fail-closed for protected PDFs, but that guard did not inspect documents inside a project container or recovery snapshot.

`useStudioDocument.restoreProject()` now inspects every distinct current, past, and future snapshot before changing active-document state. A password-protected or otherwise unverifiable PDF rejects the entire restore, leaving existing document state untouched; `/studio` reports a safe message and does not create a preview session. Plain project and recovery PDFs continue through the prior flow. Legacy Studio has no Device mode or approved protected-PDF preparation route, so encrypted inputs remain intentionally unsupported there.

| Reachable path | Protected-input behavior and boundary | Cloud submission / request-start record | Browser evidence |
|---|---|---|---|
| Welcome uploader, drag-and-drop, and sidebar replacement | Shared `PdfUploader` defaults to `fail-closed`; protected or uninspectable PDFs are rejected before `onFilesAccepted` and cannot replace the active document. Plain PDFs remain accepted. | Active plain documents are posted to `/api/conversion/preview/session`; `ServerPdfRenderer` records a conservative attempt immediately before `fetch`. Later binary tool calls use the shared `uploadAndDownloadFile` marker. | Protected initial upload/replacement and plain Rotate cases passed in the privacy suite. |
| `.pns` project import | `openProject()` reconstructs embedded Files, then `restoreProject()` inspects current, past, and future snapshots before activating any of them. Protected or unverifiable snapshots fail closed. | Rejected projects never reach the automatic preview POST or a processing endpoint. | Synthetic encrypted current-document and past-history projects were rejected with zero preview or processing POSTs. ## M1-S2-05 Studio V2 export and immutable snapshot qualification

Source contract: Studio V2 accepts a PDF only after the user authorizes a Cloud session upload. That consent authorizes transmission; it is not a password or output-protection choice. The upload route accepts one `file` part and does not accept a PDF password. The Go upload path validates PDF structure and rejects encrypted source PDFs. No reviewed product copy or API contract promises that Studio V2 exports preserve source encryption. Finalization materializes the selected VDM as a normal plaintext PDF. Source protection and exported-result protection are therefore separate, and no automatic password preservation was added.

The backend trust chain is session identity/expiry → session document → active immutable version → version VDM → materialized snapshot → export record → authenticated export download. Finalization locks the session and checks that its active version remains the requested version before recording a snapshot or export. Export rows retain the exact document and version IDs; changing the active version does not rebind an older export. Download resolution independently checks session ownership, document association, session expiry, and export expiry before resolving the object. The response omits internal storage keys. Queued operation reconciliation can create versions, but this task did not change the coordinator; finalization uses only the version active when its repository checks succeed.

The cache-hit path previously trusted a snapshot pointer, same-document asset and object existence. It did not compare the snapshot's version/page count or validate the stored PDF bytes. `loadVerifiedSnapshot` now requires the snapshot to match the requested immutable version and VDM page count, the asset to belong to the document and use one of the source-confirmed snapshot/materialized/job-result types with PDF MIME and positive recorded size, and the stored object to parse as a nonempty PDF with the expected page count and byte size. Finalization rejects a broken pointer/object and creates no export record; the by-version-ID materializer may instead rebuild from that version's authoritative VDM when a cache is missing or invalid. Cache reuse now resolves the object once and passes that validated local file forward, avoiding an immediate duplicate storage download.

This is fail-closed hardening for inconsistent persisted metadata and missing/corrupt storage objects. Tests construct those states directly; they do not demonstrate that ordinary application requests can create a cross-version pointer. Snapshot rows and storage keys are treated as immutable by existing writers, but the schema has no content digest binding bytes to the snapshot record. On every cache-hit finalization, the backend now downloads and parses the object and checks its size/page count; this adds I/O and parsing cost, especially for large exports. Same-size valid-object replacement is not cryptographically excluded. A storage checksum/integrity contract would need separate design.

Backend tests exercise local PostgreSQL repository transactions and local temporary object storage, including identity A/B, unknown IDs, expiry, old-export version binding, cached-snapshot mismatch/corruption/missing-object rejection, cache-miss materialization, page count and text order. The successful synthetic plaintext export is independently checked after `ResolveDownload` using qpdf, pdfinfo and pdftotext; it is a PDF with the expected page count/content and `Encrypted: no`, matching the actual Studio V2 contract.
