## Product wording versus source behavior

### Product-documented wording

- The shared [ProcessingModeSelector](../../../components/shared/ProcessingModeSelector.tsx#L131-L140) says Device processing runs entirely in the browser, the file stays on the device, and in one billing branch says it keeps data private. That claim applies to the selected execution mode, but the shared uploader can already send a protected source to the Cloud unlock endpoint before the workspace and venue selector are reached.
- Lock and Unlock are explicit transformations. Lock promises an encrypted output in its workspace copy; Unlock deliberately returns an unprotected PDF. These are different from ordinary document-editing transformations.
- Some public tool guidance accepts a password-protected PDF when the correct password is supplied. It does not specify the output encryption algorithm, owner/user-password relationship, PDF permissions, or whether those properties must match the input.

### Source-confirmed behavior

- The shared [`PdfUploader`](../../../components/pdf/PdfUploader.tsx#L70-L92) checks for encryption and queues protected files. On “Unlock & Continue,” it sends the original encrypted bytes and entered password to `/api/security/unlock`, then wraps the decrypted bytes in a new `File` with an `originalPassword` property before passing it to the route callback ([lines 122–157](../../../components/pdf/PdfUploader.tsx#L122-L157)). The ordinary tool route mounts this uploader before navigating to the workspace ([tool page lines 92–109 and 194–200](../../../app/%28site%29/%5BtoolId%5D/page.tsx#L92-L109)).
- [`ExecutionManager.run`](../../../lib/execution/ExecutionManager.ts#L62-L95) directs explicit Cloud requests and any unsupported or flag-disabled client operation to `CloudExecutor` before it reaches the explicit Device branch. Its Device branch rejects safety-gate failures locally ([lines 133–179](../../../lib/execution/ExecutionManager.ts#L133-L179)), but on `UNSUPPORTED_CLIENT_OP` with a password it attempts Cloud execution ([lines 180–210](../../../lib/execution/ExecutionManager.ts#L180-L210)). Auto has a separate permitted Cloud fallback for most client errors while preserving validation, decryption-authentication, and cancellation failures ([lines 269–343](../../../lib/execution/ExecutionManager.ts#L269-L343)).
- [`ClientExecutor`](../../../lib/execution/ClientExecutor.ts#L22-L51) declares supported tools. Several handlers pass `originalPassword` to a local processor, while the pdfcpu watermark and add-text operations reject protected input as unsupported ([`pdfcpuClient.ts` watermark](../../../lib/execution/pdfcpu/pdfcpuClient.ts#L261-L272), [add text](../../../lib/execution/pdfcpu/pdfcpuClient.ts#L417-L428)). An explicit Device request can therefore reach the manager's password-triggered Cloud route after a local limitation.
- [`CloudExecutor`](../../../lib/execution/CloudExecutor.ts#L63-L82) appends per-input `password_i` and first-input `file_password` fields and calls the common API helper. For one-file work, the helper reads only `formData.get("file")` and obtains restoration metadata from that `File` ([`lib/api.ts` lines 285–295](../../../lib/api.ts#L285-L295)). It announces 100% progress before attempting restoration ([lines 323–337](../../../lib/api.ts#L323-L337)); if a PDF has `originalPassword`, it posts to `/api/security/lock`, but catches any failure and returns the original processing Blob ([lines 338–365](../../../lib/api.ts#L338-L365)). It does not independently inspect whether a successful lock response is encrypted or structurally valid.
- Merge uses repeated `files` fields in Cloud multipart construction, while the shared helper's restoration lookup is for singular `file`. The Go [merge controller](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/structure/controller.go#L31-L77) accepts multiple file field names and sends staged paths to [`MergePDFs`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/structure/merge.go#L12-L24), which uses a default pdfcpu configuration. The upload middleware stages file parts but does not pass password fields to the merge function ([backend `Prepare`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/uploads/middleware.go#L57-L111)). The source does not establish an output-password rule for multiple inputs.
- The backend lock service uses the same supplied password for user and owner password with AES-128 ([`lock.go`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/security/lock.go#L12-L24)); its controller returns an encrypted PDF response and removes its temporary file ([`security/controller.go`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/security/controller.go#L27-L61)). This is not evidence that it preserves the input algorithm, permissions, or user/owner distinction.
- The workspace normally stores a returned Blob only after `ExecutionManager.run` resolves. The shared helper's swallowed re-lock error resolves with the unprotected processing Blob, so that normal success path can publish it as a completed result. PDF-to-text has a distinct non-PDF output; its Cloud OCR path may submit an asynchronous task, so PDF password restoration does not apply to the returned text artifact.
- Legacy Studio has direct API callers that bypass `ExecutionManager` and share `PdfUploader`/`uploadAndDownloadFile`; the singular-file helper behavior therefore also applies to some of those flows. Studio V2 has a separate session/job API and bypasses both the manager and this helper for its managed operations. Its protected-input and output contract needs separate acceptance evidence; this report does not infer that it has the same restoration behavior.
- Cross-tool download state carries Blob/name/MIME data but no `originalPassword` field ([`WorkflowContext.tsx`](../../../context/WorkflowContext.tsx) and [download transfer](../../../app/%28site%29/%5BtoolId%5D/download/page.tsx#L50-L85)). Whether a target tool re-prompts or should preserve protection across a transfer remains undefined.

## Call-path map and publication boundary

```text
ordinary tool route
  -> PdfUploader encryption check
     -> /api/security/unlock before workspace/venue selection
     -> decrypted File + originalPassword metadata
  -> workspace
     -> ExecutionManager.run (most tool workspaces)
        -> Device client, CloudExecutor, or Auto fallback
     -> direct Studio API (legacy) or Studio V2 session/job API (separate paths)
  -> uploadAndDownloadFile for shared Cloud/direct calls
     -> process response Blob
     -> progress 100 is emitted
     -> optional /api/security/lock
        -> failure is logged and swallowed
     -> Blob returned
  -> workspace/download state can publish resolved Blob
```

For canonical workspaces, the promise resolution from `ExecutionManager.run` commonly precedes `setDownloadData`. The common helper's catch block makes a failed re-lock appear as a resolved operation; the caller has no protection signal with which to block publication. For queued OCR and Studio V2, result creation is owned by separate APIs and must be traced/tested independently.

## Decisions requiring approval

1. **Device venue before password entry.** Decide whether protected input can ever be unlocked in Cloud before the user selects a venue. A Device claim is contradicted if source bytes/password reach Cloud first. Preferred direction: collect venue consent before any Cloud unlock and make unsupported Device operations reject locally.
2. **Transformation output policy.** Decide which ordinary PDF operations preserve access protection, whether failure to restore protection is a hard processing failure, and what metadata must match the input.
3. **Meaning of equivalent protection.** State whether preserving a password also preserves encryption algorithm/key strength, user versus owner passwords, and permissions. Current backend lock uses AES-128 and the same password for both roles, so matching the entered user password alone is not equivalent.
4. **Merge with multiple passwords.** Choose reject, ask for a new output password, or another explicit policy for multiple inputs (including different passwords). Do not use the first input password by assumption.
5. **Non-PDF and intentional unlock outputs.** Confirm explicit exceptions for Unlock and outputs such as text, images, or Word. Password restoration should not be applied to these artifacts by default.
6. **Cross-tool transfers.** Decide whether the target asks for the password again or carries sensitive metadata in a controlled way. Current transfer state omits `originalPassword`.
7. **Studio and Studio V2.** Decide whether each is in scope for the same venue and protection contract, then give each direct/queued publication path an owner and separate acceptance tests.
8. **Sign semantics.** Confirm whether product wording means a visible mark or a cryptographic digital signature; the inspected local path supports only a visual mark.

These decisions require product-owner approval where they define user-facing behavior and technical-lead approval for the implementation/security contract. No ambiguous rule has been silently converted into a passing assertion.

## PR #22 integration assessment

As checked during Stage 0, [PR #22](https://github.com/gimesha-adikari/pdfnest/pull/22) is **OPEN**, not draft, based on `main` at `0f4323f5bd95263b6cb8fcd97e017e75e10c3b4b`, and has head `e084e3e076b5f3eb4a91b3c24739b7e4f90f8fe2` on `release/gim-43-device-mode-safety`. GitHub reports merge state `CLEAN` and no review decision. At inspection, Frontend CI, Codeac, Vercel preview, and Vercel Preview Comments were successful.

Its four changed files are `lib/execution/ExecutionManager.ts`, `lib/execution/flags.ts`, `tests/unit/deviceModeSafety.test.ts`, and `tests/unit/flags.test.ts`. The implementation makes explicit Device requests fail closed for unsupported/disabled local operations and removes the password-related Device-to-Cloud fallback; Auto and explicit Cloud behavior are retained. The flag change replaces dynamic `process.env` indexing with explicit static readers for public per-tool flags so Next.js can inline those values; it does not change the boolean parser. Its new Device tests cover those manager paths, and both new/updated test files match the existing unit-runner discovery on the milestone branch.

It does **not** change the shared uploader's pre-workspace Cloud unlock and does not change `uploadAndDownloadFile`'s swallowed re-lock failure. It therefore only partially addresses F-01 and does not address F-02.

**Approved Milestone 1 integration order:**

1. Preserve original PR #22.
2. Integrate its original commit into the Milestone 1 development branch.
3. Verify manager behavior against the Stage 0 regression assertions.
4. Continue the remaining privacy and publication work on unreleased development branches.
5. Consider production merges only after milestone qualification and explicit user approval.

Do not merge PR #22 into `main` as a prerequisite to Milestone 1 development; a default-branch merge may trigger automatic production deployment.

## M1-S1-01 manager integration status

The exact PR #22 head `e084e3e076b5f3eb4a91b3c24739b7e4f90f8fe2` was merged into `milestone-1/privacy-protected-artifacts` with non-fast-forward merge commit `07153ebb0cf80e05ba577126a52e99c128d2e677`. The merged manager now fails explicit Device requests closed for unsupported operations, disabled client flags, password-related local limitations, generic client errors, and safety-gate rejections. The seven Stage 0 F-01 manager assertions pass on this branch. The ordinary `deviceModeSafety.test.ts` suite also checks successful Device execution, no fallback, telemetry mode/error reporting, Auto routing, and explicit Cloud routing.

This is only the execution-manager portion of F-01. `PdfUploader` still sends protected source bytes and the entered password to `/api/security/unlock` before workspace navigation and before the workspace's venue selector is available. **Passing `ExecutionManager` tests does not prove that explicit Device processing keeps the entire document preparation path local.** This is the next F-01 implementation boundary. The independent F-02 re-lock/publication vulnerability remains unresolved.
