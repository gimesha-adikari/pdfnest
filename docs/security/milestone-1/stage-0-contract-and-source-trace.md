## Product wording versus source behavior

### Product-documented wording

- The shared [ProcessingModeSelector](../../../components/shared/ProcessingModeSelector.tsx#L131-L140) says Device processing runs entirely in the browser, the file stays on the device, and in one billing branch says it keeps data private. That claim applies to the selected execution mode, but the shared uploader can already send a protected source to the Cloud unlock endpoint before the workspace and venue selector are reached.
- Lock and Unlock are explicit transformations. Lock promises an encrypted output in its workspace copy; Unlock deliberately returns an unprotected PDF. These are different from ordinary document-editing transformations.
- Some public tool guidance accepts a password-protected PDF when the correct password is supplied. It does not specify the output encryption algorithm, owner/user-password relationship, PDF permissions, or whether those properties must match the input.

### Source-confirmed behavior

- The shared [`PdfUploader`](../../../components/pdf/PdfUploader.tsx#L70-L92) checks for encryption and queues protected files. On “Unlock & Continue,” it sends the original encrypted bytes and entered password to `/api/security/unlock`, then wraps the decrypted bytes in a new `File` with an `originalPassword` property before passing it to the route callback ([lines 122–157](../../../components/pdf/PdfUploader.tsx#L122-L157)). The ordinary tool route mounts this uploader before navigating to the workspace ([tool page lines 92–109 and 194–200](../../../app/%28site%29/%5BtoolId%5D/page.tsx#L92-L109)).
- [`ExecutionManager.run`](../../../lib/execution/ExecutionManager.ts#L62-L95) directs explicit Cloud requests and any unsupported or flag-disabled client operation to `CloudExecutor` before it reaches the explicit Device branch. Its Device branch rejects safety-gate failures locally ([lines 133–179](../../../lib/execution/ExecutionManager.ts#L133-L179)), but on `UNSUPPORTED_CLIENT_OP` with a password it attempts Cloud execution ([lines 180–210](../../../lib/execution/ExecutionManager.ts#L180-L210)). Auto has a separate permitted Cloud fallback for most client errors while preserving validation, decryption-authentication, and cancellation failures ([lines 269–343](../../../lib/execution/ExecutionManager.ts#L269-L343)).
- [`ClientExecutor`](../../../lib/execution/ClientExecutor.ts#L22-L51) declares supported tools. Several handlers pass `originalPassword` to a local processor, while the pdfcpu watermark and add-text operations reject protected input as unsupported ([`pdfcpuClient.ts` watermark](../../../lib/execution/pdfcpu/pdfcpuClient.ts#L261-L272), [add text](../../../lib/execution/pdfcpu/pdfcpuClient.ts#L417-L428)). An explicit Device request can therefore reach the manager's password-triggered Cloud route after a local limitation.
- [`CloudExecutor`](../../../lib/execution/CloudExecutor.ts#L63-L82) appends per-input `password_i` and first-input `file_password` fields and calls the common API helper. For one-file work, the helper reads only `formData.get("file")` and obtains restoration metadata from that `File` ([`lib/api.ts` lines 285–295](../../../lib/api.ts#L285-L295)). It announces 100% progress before attempting restoration ([lines 323–337](../../../lib/api.ts#L323-L337)); if a PDF has `originalPassword`, it posts to `/api/security/lock`, but catches any failure and returns the original processing Blob ([lines 338–365](../../../lib/api.ts#L338-L365)). It does not independently inspect whether a successful lock response is encrypted or structurally valid.
- Merge uses repeated `files` fields in Cloud multipart construction, while the shared helper's restoration lookup is for singular `file`. The Go [merge controller](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/structure/controller.go#L31-L77) accepts multiple file field names and sends staged paths to [`MergePDFs`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/structure/merge.go#L12-L24), which uses a default pdfcpu configuration. The upload middleware stages file parts but does not pass password fields to the merge function ([backend `Prepare`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/uploads/middleware.go#L57-L111)). The source does not establish an output-password rule for multiple inputs.
- The backend lock service uses the same supplied password for user and owner password with AES-128 ([`lock.go`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/security/lock.go#L12-L24)); its controller returns an encrypted PDF response and removes its temporary file ([`security/controller.go`](https://github.com/gimesha-adikari/pdfnest-backend/blob/296838852195f96ca5590b3466a33ec5ae3e39d9/internal/security/controller.go#L27-L61)). This is not evidence that it preserves the input algorithm, permissions, or user/owner distinction.
- The workspace normally stores a returned Blob only after `ExecutionManager.run` resolves. The shared helper's swallowed re-lock error resolves with the unprotected processing Blob, so that normal success path can publish it as a completed result. PDF-to-text has a distinct non-PDF output; its Cloud OCR path may submit an asynchronous task, so PDF password restoration does not apply to the returned text artifact.
- Legacy Studio has direct API callers that bypass `ExecutionManager` and share `PdfUploader`/`uploadAndDownloadFile`; the singular-file helper behavior therefore also applies to some of those flows. Studio V2 has a separate session/job API and bypasses both the manager and this helper for its managed operations. Its protected-input and output contract needs separate acceptance evidence; this report does not infer that it has the same restoration behavior.
- Cross-tool download state carries Blob/name/MIME data but no `originalPassword` field ([`WorkflowContext.tsx`](../../../context/WorkflowContext.tsx) and [download transfer](../../../app/%28site%29/%5BtoolId%5D/download/page.tsx#L50-L85)). Whether a target tool re-prompts or should preserve protection across a transfer remains undefined.

## Call-path map and publication boundary

```text
ordinary tool route
  -> PdfUploader encryption check
     -> /api/security/unlock before workspace/venue selection
     -> decrypted File + originalPassword metadata
  -> workspace
     -> ExecutionManager.run (most tool workspaces)
        -> Device client, CloudExecutor, or Auto fallback
     -> direct Studio API (legacy) or Studio V2 session/job API (separate paths)
  -> uploadAndDownloadFile for shared Cloud/direct calls
     -> process response Blob
     -> progress 100 is emitted
     -> optional /api/security/lock
        -> failure is logged and swallowed
     -> Blob returned
  -> workspace/download state can publish resolved Blob
```

For canonical workspaces, the promise resolution from `ExecutionManager.run` commonly precedes `setDownloadData`. The common helper's catch block makes a failed re-lock appear as a resolved operation; the caller has no protection signal with which to block publication. For queued OCR and Studio V2, result creation is owned by separate APIs and must be traced/tested independently.

## Decisions requiring approval

1. **Device venue before password entry.** Decide whether protected input can ever be unlocked in Cloud before the user selects a venue. A Device claim is contradicted if source bytes/password reach Cloud first. Preferred direction: collect venue consent before any Cloud unlock and make unsupported Device operations reject locally.
2. **Transformation output policy.** Decide which ordinary PDF operations preserve access protection, whether failure to restore protection is a hard processing failure, and what metadata must match the input.
3. **Meaning of equivalent protection.** State whether preserving a password also preserves encryption algorithm/key strength, user versus owner passwords, and permissions. Current backend lock uses AES-128 and the same password for both roles, so matching the entered user password alone is not equivalent.
4. **Merge with multiple passwords.** Choose reject, ask for a new output password, or another explicit policy for multiple inputs (including different passwords). Do not use the first input password by assumption.
5. **Non-PDF and intentional unlock outputs.** Confirm explicit exceptions for Unlock and outputs such as text, images, or Word. Password restoration should not be applied to these artifacts by default.
6. **Cross-tool transfers.** Decide whether the target asks for the password again or carries sensitive metadata in a controlled way. Current transfer state omits `originalPassword`.
7. **Studio and Studio V2.** Decide whether each is in scope for the same venue and protection contract, then give each direct/queued publication path an owner and separate acceptance tests.
8. **Sign semantics.** Confirm whether product wording means a visible mark or a cryptographic digital signature; the inspected local path supports only a visual mark.

These decisions require product-owner approval where they define user-facing behavior and technical-lead approval for the implementation/security contract. No ambiguous rule has been silently converted into a passing assertion.

## M1-S1-02R route-policy correction

The landing page now obtains a protected-PDF policy from the registered route's actual file type, execution policy, and client/offline capability, with explicit route overrides for workflows that do not carry the selected venue into their direct submission branches. Registered Device/Auto/Cloud workspaces retain their mode. Backend-only direct/API/queued routes do not offer Device as an execution venue: protected input can be prepared locally, then an explicit, route-scoped Cloud-processing authorization is required both at the workspace gate and immediately before submission. This applies to PDF-to-Word, Grayscale, PDF-to-Markdown, PDF Editor, Redact, OCR Text V2, OCR-aware Markup V2, and Structured Document V2. Legacy Highlight, Underline, and Strikeout retain their normal unprotected routes but require a protected-input Cloud-consent gate because their OCR/worker branches directly submit files. PDF-to-Text keeps Device/Auto/Cloud execution; protected Cloud OCR has a separate confirmation after any Cloud unlock. Unlock is an explicit operation; Studio V2 keeps its separate Cloud session-upload consent. The unregistered legacy `/studio` route, `/searchable-pdf-v2`, `/image-to-searchable-pdf`, and future routes without a qualified PDF contract are unqualified and fail closed for protected input; the latter searchable-PDF routes accept images rather than PDFs in their intended input flow.

Plain PDFs inspected as unprotected keep the existing Cloud route without an extra protected-input consent step. Cloud-unlock consent is distinct from permission to send the prepared file to a Cloud transformation. PDF-to-Text asks again before its explicit Cloud OCR branch and records that submission; Auto fallback remains unchanged and transmission provenance is recorded on the manager's safety-rejection Cloud path. The shared mode selector applies the same Cloud-transmission eligibility rule to both Device entry points, and `ExecutionManager` locally rejects a stale explicit Device request for a Cloud-transmitted input before invoking either executor. Previously Cloud-transmitted sources retain that state across protected-input queues and transfers; they cannot be represented as never having left the device. Mixed batches replace each protected file in its original selection position and retain the password association with that source. Cross-tool transfer carries only transient source-lineage/transmission flags, re-inspects the new File, and does not infer that output encryption matches input encryption.

The 26-case Playwright suite passed with synthetic fixtures, a local Next.js app, and intercepted local API mocks. It checks direct PDF-to-Word and queued Structured Document submissions after authorization, separate authorization after Cloud unlock for PDF-to-Text OCR, protected annotation route gating, request payload/order, Device/Auto preparation, the Cloud-offline selector bypass, normal venue selection for eligible plain PDFs, mixed Merge order/passwords, cancellation/stale responses, Cloud-transmitted cross-tool transfer to PDF Editor, plain PDF compatibility, explicit Unlock, legacy Studio protected-input blocking, and Studio V2 session-upload consent. This is browser-to-mock evidence, not real-backend, production-browser, or protected-output validation. Uncovered legacy/direct endpoints and routes without a qualified capability remain an F-01 audit boundary. F-01 is not fully verified or closed; the independent F-02 re-lock/publication vulnerability remains unresolved and unchanged.

## M1-S1-04R cross-identity worker-deduplication correction

## M1-S2-06 queued PDF task publication trace

The representative producer is the Image to Searchable PDF workspace. Its catalog contract is `BACKEND_ONLY`, and the shared mode selector says it runs on Platen Cloud. The user action “Create Searchable PDF” initiates the image upload; the workspace's `requireAuth` gate authenticates the action but is not a separate Cloud-consent dialog. This path accepts images, not protected PDF bytes, and submits no input password. It uploads image bytes to user-owned storage keys, then calls `/api/ocr/jobs` with JSON task parameters and those storage references. The Go controller resolves the authenticated user identity, validates key ownership, reserves billing, registers the task with that identity, and processes images asynchronously. A completed artifact is an ordinary readable PDF generated from supplied images; neither frontend wording nor backend source promises preservation of an input PDF password.

The artifact transition is now: accepted owner-bound registry entry → processing → generated file → PDF page/structure validation → durable local or object storage under a task-specific output key → billing commit → owner-preserving `COMPLETED` transition. If registration fails, the handler returns 503 before launching the processor and releases the reservation/request-owned uploaded image objects. If processing, PDF validation, storage, billing, or the terminal transition fails, it does not publish a completed result; an unreferenced persisted output is removed when the terminal state rejects it. The local task path is retained only in the server registry. The current `/api/ocr/jobs` route has no idempotency middleware/key and creates a fresh UUID per accepted POST. UI duplicate-click suppression and operation generations prevent the selected workspace from conflating results, but an explicit retry after an uncertain HTTP response may create an additional independent task; that case is not integrated-tested. Source review found billing commit occurs immediately before the terminal-state compare-and-set; cancellation can win after commit but before completion, leaving a cancelled task with no artifact while billing may already be committed. This narrow billing race was not reproduced or changed.

The status and progress wire representation is a projection containing task ID, status, progress, safe error, update time, and the existing capability token. It omits storage key/path, owner identity, and billing reservation fields. The same projection is used by polling, cancellation responses, and WebSocket progress. The authorized owner uses the existing capability token to build `/api/v1/download/:id?token=...`; the task's status or download handler validates owner/capability independently. Download is allowed only for `COMPLETED`, and absent, expired, or missing stored artifacts fail with safe errors. The response projection change preserves fields consumed by this repository's frontend; external clients that relied on undocumented result paths were not inspected.

The selected R2 route no longer accepts an empty user identity and fails closed if owner registration cannot be recorded. A source review also found that the older `/api/ocr/image-to-text-pdf` local-storage fallback used generic `TaskRegistry.Set` for successful PDF completion after owner-bound registration. If its Redis task record had expired, the generic setter could recreate a completed record with no owner. A Miniredis/Fiber test reproduced the authorization consequence: a different identity without a capability received HTTP 200 for both task status and artifact download. The shared status/progress/download authorization now requires a matching owner or the exact per-task capability even when `OwnerIdentity` is empty, and the local searchable-PDF fallback now calls `SetWithResultURL` with its captured owner and reservation. A second reproduction showed that an unrelated identity could issue `DELETE` against an ownerless completed task and receive its `downloadToken` in the terminal status response. The atomic cancel operation now requires a matching owner or exact task capability before changing state or returning terminal data; the unauthorized response contains no token, while a valid capability still resolves the completion/cancellation race. The new regression returns 403 without the synthetic capability and 200 with it for authorized status/download/terminal resolution. This is controlled registry/handler evidence, not a live OCR worker run.

At the frontend, task completion remains a server status, not a progress percentage. The Image workspace verifies task ID and operation generation, downloads the artifact, uses PDF.js to parse a nonempty PDF with a readable first page, then publishes the Blob and navigates. Empty, malformed, HTML/JSON and arbitrary binary results fail. The validator does not prove every page is readable, OCR content accuracy, page equivalence, or encryption. A controlled browser test reproduced the former behavior by marking a mocked task `COMPLETED` and returning malformed bytes with HTTP 200 and PDF MIME; before correction that result was published as `.pdf`. The selected workspace supplies authoritative external status, and all current tracker call sites found in the frontend pass status, so the fallback is unreachable in the tested consumer. It remains unqualified for a hypothetical future status-less caller. Polling and cancellation in `useAsyncTask` require a matching task ID and server-reported `COMPLETED`; duplicate callback delivery is suppressed.
